# Multi-user layer for 9Router

A complete multi-tenant subsystem bolted onto 9Router: user registration and login with JWT sessions, per-user API key management via a linking table, daily quota enforcement in the chat handler, an admin CRUD surface, a client-side portal UI, and 36 Playwright e2e tests. The entire feature is gated behind `MULTI_USER_MODE=true`, which keeps the existing single-user deployment path untouched. The approach is sound — a linking table (`userApiKeys`) avoids schema changes to the existing `apiKeys` table, and quota enforcement is injected into the chat handler with a dynamic import to keep the critical path fast when disabled.

**Watch for:** Full API key values are returned in the GET /keys response, making any key extractable after creation (confirmed). The UI delete-key button is broken — it sends the ID in the request body but the server reads from the query string (confirmed). No mechanism exists to promote the first registered user to admin (confirmed). The quota check is non-atomic with request processing, so concurrent requests can exceed the daily limit (likely). User deletion leaves orphaned API keys that remain valid for LLM access (confirmed).

## High-level view

The database layer extends the existing schema declaratively — a `users` table and a `userApiKeys` junction table are appended to the `TABLES` object in schema.js, so the auto-sync mechanism picks them up without a numbered migration. No rollback story exists if the tables need to be altered later.

Session management uses a separate JWT secret (auto-generated to a file in DATA_DIR if unset). The JWT carries `userId`, `username`, and `role` with 7-day expiry. A deactivated or role-changed user's token remains cryptographically valid, but the middleware re-checks `isActive` from the database on every authenticated request, so revocation is effective within one API call.

Quota enforcement happens at check-time, not at record-time. The chat handler calls `checkQuotaForApiKey` before forwarding the request, but the usage record is written after the upstream response. Under concurrency, N requests can all pass the check before any of them are recorded. For daily limits of 1000, the overshoot is bounded by the user's parallel request count.

The dashboard guard passes all `/api/multi/*` paths through without admin auth, relying on each route handler to enforce its own user-token auth. A missing `requireUserAuth` call in any future route under that prefix would be a silent auth bypass.

The user portal stores the JWT in localStorage and attaches it via `Authorization: Bearer` headers. No CSRF exposure (bearer tokens aren't auto-sent), but any XSS in the same origin can exfiltrate the token.

1. **API keys returned in full on GET** — The keys list endpoint returns unmasked `key` values. Any authenticated request to GET /api/multi/keys exposes all key values in the network response. Mask keys in the list response and only return the full value on POST creation. (confirmed)
2. **No admin bootstrap path** — The first registered user gets `role: 'user'`. New deployments have no way to reach admin endpoints without direct DB access. Add a "first user becomes admin" rule or an env-var-gated bootstrap. (confirmed)
3. **In-memory rate limiter is ephemeral** — `loginAttempts` Map resets on process restart and is per-instance behind a reverse proxy. Consider persisting attempts in SQLite or document the limitation. (confirmed)
4. **localStorage token storage** — JWT in localStorage is readable by any XSS payload. If the deployment is internet-facing with third-party scripts, an httpOnly cookie would be safer. Document the threat model. (confirmed)
5. **Quota TOCTOU under concurrency** — `checkQuotaForApiKey` reads current usage, but the usage record is written after the upstream response completes (5-30s for streaming). Parallel requests all pass the check. For strict enforcement, a counter-based reserve-then-commit pattern is needed. (likely)
6. **DELETE key client/server mismatch** — The UI sends the key ID in the request body, but the server reads it from `searchParams.get("id")`. The UI delete button always returns 400. Fix either side. (confirmed)
7. **Password length upper bound missing** — bcrypt truncates input at 72 bytes. A user with a longer password has less entropy than they believe. Cap at 72 characters or pre-hash. (confirmed)
8. **User deletion orphans API keys** — `deleteUser` removes from `users` and `userApiKeys` but not from `apiKeys`. Orphaned keys remain valid for LLM API access. Cascade the delete or mark keys inactive. (confirmed)

<summary>Details</summary>

## API key exposure in list endpoint

The GET handler in `/api/multi/keys/route.js` selects the full `key` column and returns it unmasked:

```javascript
const keys = db.all(`SELECT id, key, name, isActive, createdAt FROM apiKeys WHERE id IN (${placeholders})`, ids);
```

The UI displays it masked via `maskKey()`, but the raw value is in the network response. Any script or browser extension can read it. This defeats the "copy it now, it won't be shown again" message shown at creation time. The fix: return only a prefix (e.g., first 8 chars) in the list response.

## Admin bootstrap gap

`createUser` in `userDb.js` hardcodes `role: "user"`. The registration endpoint has no special-case for the first user. The admin test suite works around this by directly updating the SQLite file with better-sqlite3. In production, a new deployment has no admin without manual DB editing. Options: (a) first-registered-user-is-admin, (b) env var `MULTI_USER_INITIAL_ADMIN=username` that auto-promotes on startup, (c) a CLI command.

## Rate limiter durability

The login rate limiter is an in-memory `Map` in `login/route.js`. Two failure modes: a process restart wipes all state (an attacker just needs patience), and behind a multi-instance deployment each instance tracks independently (effective limit multiplies by instance count). Storing attempts in SQLite would survive restarts and be shared in single-DB deployments.

## Quota enforcement timing

The quota check in `chat.js` (lines 80-88) queries `usageHistory` for today's records. Usage is recorded by `usageRepo.js` after the upstream response is processed. The window between check and record is the full duration of the upstream LLM call. For token-based limits, a single large response can push usage well past the limit if it arrives after concurrent checks. A reservation pattern (increment a counter before forwarding, decrement on failure) would close this gap.

## DELETE request body vs query string mismatch

In `keys/page.js`, `handleDelete` sends the key ID in the JSON body:

```javascript
const res = await fetch('/api/multi/keys', {
  method: 'DELETE',
  headers: authHeaders(),
  body: JSON.stringify({ id }),
});
```

But the server in `keys/route.js` reads it from the URL:

```javascript
const keyId = searchParams.get("id");
```

The DELETE from the UI always hits the `"Key ID is required"` 400 response. The e2e test (`keys.spec.js`) works because it uses `request.delete('/api/multi/keys?id=...')` with the query param directly — it never exercises the actual UI code path.

## User deletion leaves orphaned API keys

In `userDb.js`, `deleteUser` runs:

```javascript
db.run(`DELETE FROM users WHERE id = ?`, [id]);
db.run(`DELETE FROM userApiKeys WHERE userId = ?`, [id]);
```

It does not delete from `apiKeys`. Those orphaned keys pass `isValidApiKey` in the chat handler (which only checks the key exists and is active), so a deleted user's keys continue to grant LLM API access indefinitely. Either cascade the delete to `apiKeys`, or at minimum set `isActive = 0` on the orphaned keys.

## Password length and bcrypt truncation

Registration validates `password.length >= 6` but sets no upper bound. bcryptjs truncates input at 72 bytes. A user who sets a 100-character password has only the first 72 bytes as their actual credential. Rejecting passwords over 72 characters or pre-hashing with SHA-256 before bcrypt is the standard mitigation.
